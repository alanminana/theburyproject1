Alcance: circuitos completos de negocio contra **SQL Server descartable** (Docker, base nueva `s2qa`, RCSI apagado y encendido) y **Playwright** (Chrome del sistema), con datos 100 % sintéticos. No se tocó ninguna base, usuario, respaldo ni credencial real; no se instaló nada del servidor.

Cómo se corre (reproducible): `scripts/qa/p07/p08_segunda_pasada.py` (regresión de los recorridos P-07, `R0`–`R11`, más los casos nuevos `S1`–`S7` de `p08_extra.py`) y `scripts/qa/a11y-responsive/crawl.js` (axe-core + HTTP + desborde + CSP en `Enforce`). Revisión de Codex: 3 hallazgos (vínculo app↔base, negativos de Caja sin control positivo ni mensaje específico, pagos concurrentes que podían aprobar sin ejercitarse) corregidos y re-ejecutados. Resultado: **192 comprobaciones, 192 correctas, con RCSI apagado (98 s) y encendido (99 s)**.

> Un HTTP 200 o una pantalla sin desbordes **no** se cuentan como prueba funcional: cada comprobación contrasta el estado en SQL (saldos, stock, movimientos de caja, auditoría) o rechaza una operación y verifica que **no** hubo efecto.

## Limitaciones declaradas

- **Lectores de pantalla reales (NVDA/JAWS/VoiceOver): no probados.** axe-core detecta solo una parte de los problemas de accesibilidad; no equivale a accesibilidad completa.
- El recorrido funcional maneja la aplicación por HTTP como un navegador (formularios reales y endpoints JSON del propio frontend) y verifica contra SQL; la interacción en navegador real (Playwright) cubre las pantallas nuevas con datos (cuentas por pagar, mora, detalle) en escritorio y móvil, más el crawler de 7 roles. Las suites E2E del repositorio corren en CI.
- Las cuotas vencidas de la sección S7 se simularon retrocediendo el vencimiento por SQL **en la base descartable** (no hay otra forma de envejecer una cuota sin esperar).
- El Chrome del sistema es la única plataforma de navegador probada.
- Facturación fiscal (externa), IVA, redondeos y costos contables: **no se tocaron**.
